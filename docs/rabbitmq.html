🐰 RabbitMQ Patterns Explained

1

Work Queue (Point-to-Point)

One message → One consumer
Producer
→
Queue
→
Consumer 1
→
Consumer 2
→
Consumer 3
⚠️ Each message is processed by ONLY ONE consumer (round-robin)

📌 When to Use

  • Task Processing: Background jobs that should run exactly once (sending emails, generating reports)
  • Payment Processing: Each payment must be processed by only one worker
  • Image/Video Processing: Heavy tasks distributed among workers
  • Data Import: Import records where each record should be processed once
  • Order Processing: Each order processed by one worker to avoid duplication

✅ Pros

  • Load balancing across workers
  • Guaranteed single processing
  • Easy to scale (add more consumers)
  • Simple to implement

❌ Cons

  • No message broadcasting
  • Can't have multiple services react
  • No routing flexibility
// Send task to queue
await publishToQueue('email-queue', { 
  to: 'user@example.com', 
  subject: 'Hello' 
});

// Process tasks (only ONE worker gets each message)
await consumeQueue('email-queue', async (msg) => {
  await sendEmail(msg);
});
2

Fanout (Broadcast)

One message → All subscribers
Producer
→
Fanout Exchange
→
Email Service
→
SMS Service
→
Push Service
✨ ALL subscribers receive the SAME message (no routing keys)

📌 When to Use

  • Notifications: Send announcements to all channels (email, SMS, push)
  • Cache Invalidation: Notify all servers to clear cache
  • Real-time Updates: Broadcast stock prices to all connected clients
  • System Events: User signup → notify analytics, email, CRM, etc.
  • Data Replication: Replicate data changes to multiple databases

✅ Pros

  • All services react to same event
  • Decoupled microservices
  • Easy to add new subscribers
  • No routing complexity

❌ Cons

  • No message filtering
  • All subscribers get everything
  • Can't route selectively
// Broadcast to all subscribers
await broadcast('announcements', { 
  title: 'Maintenance Alert', 
  message: 'System down at 2am' 
});

// Subscriber 1: Email Service (gets message)
await subscribeToBroadcast('announcements', async (msg) => {
  await sendEmails(msg);
});

// Subscriber 2: SMS Service (gets SAME message)
await subscribeToBroadcast('announcements', async (msg) => {
  await sendSMS(msg);
});

Routing Key Patterns:
• * = matches exactly one word (e.g., auth.* matches auth.error, auth.info)
• # = matches zero or more words (e.g., log.# matches log.error, log.auth.error)
• Exact match: auth.error only matches auth.error

📌 When to Use

  • Logging Systems: Route logs by severity/service (error monitor gets *.error)
  • Event Routing: Different services subscribe to relevant events
  • Monitoring: Route metrics by type (cpu.*, memory.*, disk.*)
  • Multi-tenant: Route messages by customer (customer.123.*, customer.456.*)
  • Geographical Routing: Route by region (us.east.*, eu.west.*)

✅ Pros

  • Flexible pattern matching
  • Multiple subscribers per pattern
  • Complex routing logic
  • Hierarchical organization

❌ Cons

  • More complex than fanout
  • Requires routing key design
  • Can be harder to debug
// Publish with routing key
await publishToExchange('logs', 'auth.error', {
  message: 'Login failed'
}, 'topic');

// Subscribe to all errors
await subscribeToExchange('logs', '*.error', async (msg, key) => {
  console.log('ERROR:', key, msg);
}, 'topic');

// Subscribe to all auth logs
await subscribeToExchange('logs', 'auth.*', async (msg, key) => {
  console.log('AUTH:', key, msg);
}, 'topic');

🎯 Message goes ONLY to queue with matching routing key

📌 When to Use

  • Priority Queues: Route tasks by priority (high, medium, low)
  • Department Routing: Route tickets by department (sales, support, billing)
  • Environment Routing: Route deploys by environment (dev, staging, prod)
  • Language Routing: Route content by language (en, es, fr)
  • Type-based Processing: Different processors for different file types

✅ Pros

  • Simple exact matching
  • Clear routing logic
  • Easy to understand
  • Faster than topic matching

❌ Cons

  • No pattern matching
  • Less flexible than topic
  • Requires exact key match
// Send to high-priority queue
await publishToExchange('tasks', 'high', {
  task: 'urgent-report'
}, 'direct');

// High-priority worker (only gets 'high' messages)
await subscribeToExchange('tasks', 'high', async (msg) => {
  await processUrgent(msg);
}, 'direct');

// Low-priority worker (only gets 'low' messages)
await subscribeToExchange('tasks', 'low', async (msg) => {
  await processBatch(msg);
}, 'direct');

📊 Quick Comparison

Pattern Routing Use When Example
Work Queue One message → One consumer Task must be processed exactly once Payment processing, email sending
Fanout Broadcast to all All services need same event Notifications, cache invalidation
Topic Pattern matching (*, #) Complex routing by categories Logging, multi-criteria routing
Direct Exact key match Simple categorical routing Priority queues, department routing

🌳 Decision Tree: Which Pattern to Use?

Does each message need to be processed by only ONE consumer?
✓ YES → Use Work Queue
Examples: Payment processing, task processing
✗ NO → Use Pub/Sub (Exchange)
Need routing?
No routing: Fanout
Simple routing: Direct
Complex patterns: Topic
